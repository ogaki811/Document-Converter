# 開発ルール (Development Rules)

本プロジェクトでは、品質と整合性を保つため、以下の「仕様駆動開発」および「実装前レビュー」プロセスを厳守します。

## 1. 仕様駆動開発 (Specification-Driven Development)

**原則: コードを書く前に、必ず仕様書を更新する。**

いかなる機能追加、バグ修正、仕様変更においても、コードを修正する前にドキュメント（`docs/仕様書.md` 等）を更新し、**「仕様書が正、コードが従」**の状態を維持してください。

## 2. 開発フロー

タスクに着手する際は、以下のステップ順に進めてください。

### Step 1: 仕様の定義・更新
*   変更内容に基づき、`docs/仕様書.md` を更新します。
*   UI/UXの挙動、バリデーションルール、エラー処理などを明確に記述します。

### Step 2: 実装計画とレビュー依頼 (Review Request)
*   実装に取り掛かる前に、**具体的な実装タスク（ToDoリスト）を作成し、ユーザー（管理者）に提示**してください。
*   どのファイルを、どのように変更するか（設計方針）を含めます。
*   **ユーザーの承認（レビュー通過）を得るまで、実装コードを書き始めてはいけません。**

### Step 3: 実装 (Implementation)
*   承認されたタスクリストに基づいてコーディングを行います。
*   既存のプロジェクト構成（React + Vite + Tailwind CSS）やLintルールに従います。

### Step 4: 検証 (Verification)
*   実装が仕様書通りであることを確認します。
*   `npm run lint` を実行し、静的解析エラーがないことを確認します。

## 3. コミット・プルリクエスト
*   コミットメッセージは明確に記述してください。
*   原則として、ドキュメントの変更とコードの変更はセットで扱います。

## 4. 再発防止策と品質保証 (Quality Assurance)

整合性の欠如による不具合（リネーム漏れ、中途半端な修正など）を防ぐため、以下のルールを徹底します。

*   **変更の原子性 (Atomicity)**: インポート名の変更とその使用箇所の修正など、論理的に一塊の変更は、可能な限り一度の操作で行い、不整合な状態を放置しないこと。
*   **即時検証**: ツールによる自動修正や手動修正の後は、必ず直ちに `npm run lint` や型チェックを実行し、コードの整合性を確認すること。
*   **シンボル確認**: 変数名やコンポーネント名を変更した際は、プロジェクト全体を検索（grep等）し、旧名称の残存がないか徹底して確認すること。
